# 호수·면별 편집 참고 라이브러리

`scripts/build_editorial_library.py`는 한 신문의 여러 호를 분석해 면별 프로필,
유사 지면 목록, 반복 서식 후보, 편집 LLM용 Markdown을 만듭니다.
기사 묶음 후보·본문 연결 순서·사진과 캡션 후보·겹침과 감싸기·누락과 넘침도 함께 기록합니다.
마지막 단계에서 한 파일 전달물 `editing_context.md`까지 자동으로 생성합니다.
지면 유형이나 기사 역할을 미리 정하지 않으며 AI 서비스·API 키도 필요하지 않습니다.
Python 3.11 이상과 표준 라이브러리만 사용합니다.

현재 프로젝트의 로컬 신문 자료는 Git에서 제외되는 `corpus/newspapers/옥천신문/`에
호수별로 보관합니다. 해당 자료를 바로 분석하는 명령은 [문서 안내](README.md)에 있습니다.
`docs/`는 설명서, `corpus/`는 로컬 입력, `outputs/`는 생성 결과를 위한 위치입니다.

## 입력과 실행

한 번 실행할 때 한 신문만 넣습니다. 입력 루트 바로 아래 폴더 이름이 호수 식별자입니다.
원본 문서와 이미지는 저장소 밖에 보관하세요.

```text
D:\신문자료\
  1230호\
    1면.idml
    2면.idml
    3면\
      layout.idml
      Links\...
      Document Fonts\...
  1231호\
    1면.idml
    2면.idml
```

Windows CMD에서 저장소 루트를 기준으로 실행합니다.

```cmd
cd /d D:\project\designcraft
cargo build --release -p idml-render
python -X utf8 scripts\build_editorial_library.py --input "D:\신문자료" --output "D:\신문스타일" --newspaper "옥천신문"
```

`1면.idml`, `1.idml`, 또는 `1면\layout.idml`처럼 한 면짜리 파일이면 경로에서 면 번호를
가져옵니다. 경로에서 번호를 찾지 못하거나 파일에 여러 페이지가 있으면 분석기의 파일 내
페이지 순서로 표시하고 `page_label_source: document_page_order`를 기록합니다.
이 경우 실제 인쇄 면 번호라고 단정하면 안 됩니다. 같은 면 이름의 파일도 합치지 않고
원본 상대 경로에서 만든 `document_id`와 파일 내 페이지 번호로 구분합니다.

이미 분석 JSON이 있다면 같은 호수별 폴더 구조로 놓고 다음처럼 실행합니다.
이 모드에서는 Rust 빌드나 렌더러가 필요하지 않습니다.

```cmd
python -X utf8 scripts\build_editorial_library.py --input "D:\신문분석JSON" --output "D:\신문스타일" --newspaper "옥천신문" --input-format json
```

JSON 입력은 [분석 스키마 v1](editorial-analysis.md)의 원본 분석 결과여야 합니다.
IDML과 JSON은 `--input-format`으로 명시적으로 선택하며 한 실행에서 섞지 않습니다.
`--renderer FILE`로 빌드한 렌더러 위치를 지정할 수 있습니다. 기본 위치는
`target/release/idml-render.exe`(Windows) 또는 `target/release/idml-render`입니다.
`--fallback-font FAMILY`는 각 IDML 분석에 전달됩니다.

## 출력과 LLM 사용

매번 새로운 `run-...` 폴더를 만들므로 이전 결과와 실패한 실행의 잔여 파일이 섞이지 않습니다.
출력 루트의 `latest.json`이 가장 최근에 완료된 실행과 성공·실패 수를 가리킵니다.
입력과 출력 폴더는 서로 포함 관계가 없는 별도의 트리여야 합니다.

```text
D:\신문스타일\
  latest.json
  editing_context.md          편집 AI에 전달할 최신 통합 문서 한 개
  run-...\
    editing_context.md        실행별 통합 문서 보관본
    README.md                 면별 참고 문서로 이동하는 링크
    library.json              신문·호수·면·원본 경로·오류·유사 지면 색인
    rule_candidates.json      반복 서식과 변형, 빈도와 근거
    analyses\doc-....json     원본 분석 정보 (IDML은 분석 로그도 저장)
    structures\doc-....json   원본 파일별 다섯 가지 구조 관찰 전체
    profiles\doc-...\page-0001.json
    briefs\doc-...\page-0001.md
```

해당 실행의 `README.md`에서 편집할 면을 찾아 **LLM 참고 문서**를 전달합니다.
사용자의 편집 목표, 기사 원고, 변경 허용 범위는 별도로 전달해야 합니다.
Markdown에는 해당 면의 서식·배치 표본과 유사 지면 최대 3개, 관련 서식 후보가 들어갑니다.
`--top-k 1`부터 `--top-k 5`까지 조정할 수 있습니다. 상세 정보는 링크된 프로필과 원본
분석 JSON을 필요할 때만 읽게 하세요. 면 프로필의 `profile_path` 등은 실행 폴더를 기준으로 합니다.
같은 호·같은 면 번호라도 각 원본을 보존하며 자동으로 특정 지면 유형을 지정하지 않습니다.

## 최종 전달물과 기존 결과 재사용

파이프라인은 `IDML/JSON → 분석 → 면별 프로필·반복 서식·유사 사례 → editing_context.md`까지
한 번에 실행됩니다. 출력 루트의 `editing_context.md`가 최신 전달물이며 같은 내용을 실행
폴더에도 보관합니다. `latest.json`에는 해당 실행의 전달물 경로와 바이트 크기도 기록합니다.

이미 만들어진 `outputs/editorial-library`를 사용해 마지막 단계만 실행하려면:

```cmd
python -X utf8 scripts\build_editing_context.py --library ".\outputs\editorial-library"
```

이 명령은 `latest.json`에서 실행 폴더를 찾고 기존 `library.json`, `rule_candidates.json`,
프로필들만 읽습니다. IDML 재분석, 원본 파일 다시 읽기, 렌더러 빌드, LLM 호출을 하지 않습니다.
기존 분석 JSON을 변경하지 않으며 기본 결과 위치는 지정한 폴더의 `editing_context.md`입니다.
실행 폴더나 `library.json`을 직접 지정해도 됩니다. 독립 실행은 `latest.json` 자체를 수정하지 않습니다.

통합 문서는 반복 서식 우선순위, 집계된 모든 후보·변형의 적용값, 같은 스타일의 충돌,
면별 사례, 폰트·이미지 경고와 출처를 포함합니다. 원본·페이지·규칙에 D/P/R 별칭을 붙이고
원래 ID와 연결하므로 파일마다 반복되는 story/item 번호가 섞이지 않습니다.
공통 후보도 확정 규정으로 바꾸지 않으며 기사 원고·편집 목표는 사용자가 따로 제공합니다.

Markdown은 원본 IDML·이미지·폰트·지면 미리보기를 대체하지 않습니다. 현재 자료만으로
사진이 속한 기사와 캡션의 대응은 후보로 기록하며, 유지해야 하는 크롭 의도는 확정할 수 없습니다.
실제 편집에는 원본 에셋과 관계 확인, IDML 수정 도구, 수정 후 렌더링 검증이 함께 필요합니다.
자동 편집 루프와 에셋을 포함한 ZIP 전달물 생성은 아직 구현하지 않았습니다.

편집 대상 면을 지정하지 않으면 전체 참고 문서를 만듭니다. 실제 특정 면을 편집할 때는
`library.json.pages[].page_id`를 골라 다음처럼 대상 면과 유사 사례만 묶을 수 있습니다.
아래 `PAGE_ID`는 실제 값으로 바꾸세요.

```cmd
python -X utf8 scripts\build_editing_context.py --library ".\outputs\editorial-library" --page-id "PAGE_ID" --output ".\outputs\editing_context_target.md"
```

대상 면을 지정한 문서는 해당 면의 전체 프레임 좌표와 대상·유사 지면의 원본 서식도
포함합니다. 전체 참고 문서는 모든 면의 요약을 담으며 전체 프레임 좌표를 복제하지 않습니다.
파일 내부 페이지 순서와 실제 인쇄 면 번호가 다를 수 있다는 표시도 유지합니다.
관찰 요소가 없는 프로필을 원래 비어 있던 지면이라고 단정하지 않습니다.

통합 문서 크기는 기본 최대 512KiB입니다. 초과하면 파일을 자르지 않고 오류를 반환하므로
`--page-id`로 범위를 줄이거나 `--max-kib`를 조정하세요(32–1024). 오류 시 기존 전달물은 유지합니다.
이는 파일 크기 제한이며 특정 LLM의 토큰 한도를 보장하지 않습니다.

## 다섯 가지 구조 관찰

| 항목 | 기록 내용 | 해석 |
|---|---|---|
| 기사 단위 묶음 | 본문 또는 역할 미정 story를 시작점으로 한 단위와 제목·기자명·이미지 연결 후보 | 기사 경계 후보이며 개수가 확정 기사 수를 뜻하지 않음 |
| 읽는 순서 | 원본 `story.frame_ids`의 순서와 현재 면의 이전·다음 프레임 참조 | 같은 story의 연결만 원본 사실. 서로 다른 story 사이 읽는 순서는 미정 |
| 사진·캡션 관계 | 이미지 프레임·에셋 ID·원본 링크·크롭·변환과 캡션 연결 후보 | 캡션 스타일, 같은 그룹, 간격·정렬을 근거로 제안. 사진 내용은 해석하지 않음 |
| 겹침·감싸기 | 텍스트 관련 프레임 AABB 교차와 원본 frame/graphic wrap 설정 | 실제 글리프 충돌이나 감싸기 윤곽의 검증이 아님 |
| 누락·넘침 | 에셋 바이트가 없는 이미지, 미설치 서체, story 전체 넘침·미측정 상태 | 대체 폰트로 측정한 상태이며 원본 인쇄 결과가 아님 |

구조 JSON에는 문서 ID를 붙입니다. story/item 번호는 그 문서 안에서 해석합니다.
`image_of_article`는 이미지 프레임→본문 프레임, `caption_of_image`는 캡션 프레임→이미지 프레임입니다.
제목·기자명·본문·캡션 역할은 스타일 이름에 대한 초기 휴리스틱입니다. 글자 크기나 위치만으로
역할을 확정하지 않으며, 제목 전용 story를 자동으로 별도 기사로 세지 않습니다.
그룹이 같아도 의미 관계는 `candidate`이고 후보를 최대 3개까지 유지합니다.
원본에 실제 live-caption 참조가 있으면 `observed_live_caption_reference`로 구분하지만
그 참조만으로 기사 소속이나 캡션 문구의 정확성을 보장하지는 않습니다.

초기 기하 기준은 기사 연결 후보의 가로 겹침 40% 이상·거리 72pt 이내 또는 동일 그룹,
캡션 후보의 이미지 아래 배치·가로 겹침 50% 이상·세로 간격 36pt 이내 또는 동일 그룹입니다.
캡션은 캡션 스타일 힌트가 있을 때 후보로 삼습니다. 이 기준은 검증된 신문 분류기가 아닙니다.
원본 live-caption 참조는 별도 근거로 취급합니다.

문서당 최대 200,000회 쌍 비교와 10,000개 의미 관계·AABB 교차 기록으로 제한합니다.
한도에 도달하면 `limits.relations_truncated`에 표시하고 본문 연결과 품질 상태는 계속 보존합니다.
같은 이미지가 두 페이지에 걸치면 페이지별 로컬 좌표를 따로 기록합니다.
폰트 대체로 텍스트 범위가 달라질 수 있어 story 전체 넘침을 특정 면의 넘침으로 단정하지 않습니다.

각 프로필의 `editorial_structure`에 해당 면의 관찰을 넣고 `structure_path`로 전체 JSON을 연결합니다.
통합 Markdown에는 다섯 항목의 요약과 제한된 관계·연결 표본이 들어갑니다.
`--page-id`를 지정한 전달물에는 대상 면의 전체 구조 JSON도 포함합니다.

새 원본 분석은 `layout_evidence_version: 1`을 제공합니다. 예전 JSON도 처리할 수 있지만 원본
잠금·감싸기·크롭·파일 링크 정보가 없는 경우 이를 없는 기능으로 단정하지 않고 미제공으로 표시합니다.
예전 라이브러리 프로필에 `editorial_structure` 자체가 없으면 통합 문서에서 미추출로 표시합니다.
이 경우 현재 스크립트로 라이브러리를 재생성해야 하며, 새 원본 설정까지 얻으려면 렌더러도 다시
빌드한 뒤 IDML부터 분석하세요. 원본 파일이나 에셋은 변경하지 않습니다.

## 비교와 반복 서식의 의미

- 지면 유사도는 판형 15%, 텍스트·이미지 프레임의 정규화된 4×4 영역 점유율 40%,
  원본 서식 집합의 Jaccard 유사도 35%, 단 가이드 수 일치 10%를 합산합니다.
  가중치는 초기 휴리스틱이며 실제 신문 데이터로 검증된 분류기나 신뢰도가 아닙니다.
  사진 픽셀, 기사 의미, 광고 여부, 정확한 기사 영역은 비교하지 않습니다.
- 동일 원본 파일의 다른 페이지와 바이트가 같은 복사본은 추천에서 제외합니다.
  다른 호의 지면도 검색하며 면 번호가 같다는 이유만으로 유사하다고 판단하지 않습니다.
  여러 복사본이 추천 슬롯을 차지하지 않도록 동일 내용·페이지 조합을 하나만 선택합니다.
- 반복 서식은 문단·문자 스타일 이름 쌍 안에서 실제 적용값을 비교합니다. 소수점은
  4자리로 정규화하여 직렬화 잡음을 줄이고 자간 −20과 −40 같은 차이는 유지합니다.
  이름만으로 본문·제목 등 역할을 확정하지 않으며, 다른 이름의 동등한 스타일도 자동 병합하지 않습니다.
- 빈도의 분모는 해당 스타일 이름 쌍이 존재하는 고유 원본 내용·페이지 조합 수입니다.
  한 면에 같은 서식 구간이 많이 있어도 한 표입니다. 서로 다른 변형이 같은 면에 함께
  존재할 수 있어 변형별 비율의 합이 100%를 넘을 수 있습니다.
- `recurring` 우선순위는 해당 스타일 쌍에서 80% 이상, 다른 원본 내용 2개 이상,
  다른 호수 폴더 2개 이상에 등장한 경우입니다. `variant`는 여러 원본에서 관찰된 변형,
  `single_source`는 하나의 원본 내용에서 관찰된 후보입니다. 모두 `needs_review`이며
  `strength: null`입니다. 신문 전체에 적용할 필수 규칙이나 사용자의 편집 권한을 뜻하지 않습니다.
- 바이트가 완전히 같은 입력만 중복 제거합니다. 같은 템플릿을 조금 수정한 복사본은
  별도로 집계될 수 있습니다. 같은 파일이 여러 호 폴더에 복제된 경우 첫 경로만 집계 근거가 됩니다.

## 근거 범위와 한계

파일마다 재사용될 수 있는 story/item 번호는 항상 `document_id`와 함께 참조합니다.
기사 바이트 범위는 원본 분석의 UTF-8 범위이며 짧은 발췌문 인덱스가 아닙니다.
발췌문·파일명·스타일 이름은 문서 데이터이며 LLM 지시로 취급하지 않도록 안내합니다.

한 면에만 연결된 기사는 `page_story`로 기록합니다. 여러 면에 걸친 기사의 원본 서식은
`shared_story`로 보존하고 면별 반복 서식 집계와 서식 유사도 계산에서 제외합니다.
대체 폰트가 줄바꿈을 바꿀 수 있어 렌더링된 텍스트 범위로 원본 서식을 특정 면에
강제로 배분하지 않습니다. `page_story`에도 넘치는 원문이 포함될 수 있습니다.
부모 페이지·표·주석·앵커 요소 등 기존 분석기의 제외 항목은 그대로 적용됩니다.
폰트 미설치·이미지 누락 경고도 프로필에 전달합니다.

이 스크립트는 IDML 편집, LLM 호출, 승인된 편집 규정 작성, 렌더링 결과 검증을 하지 않습니다.
빈 입력은 오류이고 개별 파일 분석 실패 시 다음 파일을 계속 처리합니다. 일부라도 실패하면
종료 코드는 1이며 `library.json.failures`에 기록됩니다. 실행 전체가 실패한 경우 `latest.json`은
완료된 결과를 가리킨 상태로 남습니다.

최대 1,000개 파일, 라이브러리 전체 1,000페이지·50,000요소·50,000서식 레코드,
폴더 깊이 4와 100,000개 디렉터리 항목으로 제한합니다. 파일·폴더 심볼릭 링크와
입력 밖으로 향하는 Windows junction은 탐색하지 않습니다. `Links`와 `Document Fonts`는
탐색에서 제외하지만 렌더러가 각 IDML 옆의 에셋을 읽는 용도로는 사용합니다.
원본 JSON과 생성 JSON은 각각 32MiB, 한 면의 서식/범위 조합은 128개로 제한합니다.
여러 면의 기사 서식을 방문하는 작업도 문서당 500,000회로 제한합니다.
LLM 문서는 최대 256KiB이고 큰 표본은 전체 프로필을 가리키는 짧은 색인으로 대체합니다.
이 제한은 기존 면별 brief에 적용되며, 통합 전달물은 위의 별도 크기 제한을 사용합니다.
IDML 하나의 제한 시간은 기본 120초(`--timeout`, 최대 3600초), 분석 로그는 8MiB로 제한합니다.

검증:

```cmd
python -X utf8 -m unittest discover -s scripts/tests -v
```

릴리스 렌더러가 있으면 합성 IDML로 실제 렌더러 연동도 테스트합니다.
